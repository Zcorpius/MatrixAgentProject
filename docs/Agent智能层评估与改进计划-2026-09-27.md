# MatrixAgent Agent/LLM 智能层专项评估与改进计划

| 项目 | 说明 |
|---|---|
| **评估对象** | MatrixAgent v0.7.1 的模型驱动能力：任务编排、上下文工程、记忆、生成体验、质量评测与迭代 |
| **代码基线** | `690adee`，2026-09-27；本次修订以实现、测试源码和已有验证记录交叉核对 |
| **评估结论** | 可靠执行与数据治理基础较完整；主要缺口是可重复的质量评测、语义检索、正文流式输出及跨任务经验复用 |
| **评分口径** | 原稿的 **6/10** 仅保留为能力覆盖的主观参考，不是任务成功率或行业基准；工程“9 分”和完成计划后“8.5～9 分”没有量化依据，不作为结论或验收承诺 |
| **评估维度** | 任务复杂度 / 编排方式 / 上下文工程 / 记忆与检索 / 生成体验 / 评测数据 / Prompt 迭代 / 模型适配与选型 |
| **验证范围** | 第一部分保留 `690adee` 的审阅基线；P0/P1/P2 六项首版均已实现，并运行确定性语料、真实模型与真机验证；效果和部署边界见各节实施状态及独立验证记录 |

> 本文区分“已实现的事实”“尚缺的能力”和“拟实施方案”。第一部分及“现状约束”描述审阅时的历史基线，不能当成实施后的现状。第二部分保留设计依据，实际落地和验收证据以各节状态及实施记录为准。优先用质量数据决定投入，不按新增技术名词数量判断 Agent 能力。

## 代码定位与执行主线

```text
ConversationCoordinator → ConversationTaskSubmitter → 调度与 AgentRuntimeRepository
                                                       ↓
                                                  AgentEngine
                                                       ↓
                           PromptContextAssembler：基础规则 + 记忆召回 + Skill
                                                       ↓
                         ModelGateway → PolicyEngine → ToolExecutor / Provider
                              ↑                              ↓
                              └───── ModelSanitizer 处理的观察结果 ─────┘
                                                       ↓
                            最终答复 / AuditRedactor 处理的轨迹 / 有限事件记忆
```

这张图表示逻辑关系，不是严格的调用时序。关键实现入口如下：

| 模型协议 | [LlmModelGateway](../matrix-agent-service/src/main/java/com/matrix/agent/model/LlmModelGateway.java)、[LlmPlanner](../matrix-agent-service/src/main/java/com/matrix/agent/model/LlmPlanner.java)、[ModelApiClient](../matrix-agent-service/src/main/java/com/matrix/agent/model/ModelApiClient.java)：原生工具调用、逐轮 JSON 兼容决策和传输 |

| 记忆 | [MemoryRouter](../matrix-agent-service/src/main/java/com/matrix/agent/data/memory/MemoryRouter.java)、[DefaultPromptBuilder](../matrix-agent-service/src/main/java/com/matrix/agent/task/prompt/DefaultPromptBuilder.java)、[RoomMemoryWriter](../matrix-agent-service/src/main/java/com/matrix/agent/data/memory/RoomMemoryWriter.java)：分层召回、投影白名单、事务内身份与 epoch 校验 |

**数据边界**：模型上下文经 `ModelSanitizer` 保留完成任务所需语义；`internalResults` 是内部保真的工具结果；`Trajectory` 经 `AuditRedactor` 处理，用于审计等用途。三者不能互换。安全落盘的轨迹不等于保留了足够语义的学习材料，本地存储也不等于数据绝不会进入云端模型请求。

## 第一部分：八个维度的现状与缺口

### 1. 默认预算面向短任务，尚无经过验证的长程模式

**已实现**：

- [AgentBudget](../matrix-agent-service/src/main/java/com/matrix/agent/task/AgentBudget.java) 默认 `maxIterations=8`、`maxToolCalls=8`、`totalDeadlineMillis=60_000`；另有单消息 8,000 字符、总输入 32,000 字符、最多 64 条消息限制。主路径预算决策仍以字符为主：当前基线的 main 源码中，`getMaxMessageTokens / getTotalInputTokens / getMaxAssistantTokens` 仅有方法定义，没有调用方（调用仅在测试中），这些字段尚未接入主路径预算裁决。端侧另有基于模型 tokenizer 的裁剪，见第 8 项。
- 预算可通过构造器注入，生产装配使用默认值，因此这是当前配置边界，不是架构只能执行 8 步的证明。
- 同会话串行，不同会话有并发执行基础。对话任务在出队构造请求时开始计算 deadline，排队等待不消耗这段预算；**60 秒是任务执行预算，不是端到端语音 SLA**。见 [TaskRequestFactory](../matrix-agent-service/src/main/java/com/matrix/agent/task/scheduler/TaskRequestFactory.java)。
- 工具以设备与应用操作为主：QQ 音乐 9 个、B 站 6 个、日历 8 个和时钟 3 个、记忆 9 个，另有计划 4 个、音量/亮度及 demo 车控等。注册入口为 `CapabilityRegistry.createRuntimeRegistry()`，实际可见集合还受用户区域与执行范围过滤。

**缺口**：缺少长程多源任务、跨执行阶段检查点和相应质量记录；当前没有通用浏览器、代码执行或 `web.search` 工具。

**评价边界**：媒体独立确认是产品授权与歧义处理规则，不能仅因多问一次用户而扣“智能分”。应度量实体理解、候选匹配、误播率、必要澄清和总交互轮数。

### 2. 原生与兼容模式均参与观察驱动循环，缺少跨任务经验闭环

- `LlmModelGateway` 支持 OpenAI、Anthropic、Gemini 原生工具调用，也支持 `STRUCTURED_JSON_COMPATIBILITY`。路由由配置决定；[ModelConfig](../matrix-agent-service/src/main/java/com/matrix/agent/contract/ModelConfig.java) 的默认值仍是兼容模式，当天媒体真机记录也使用兼容模式，不能笼统把原生模式称为当前默认运行路径。
- 当前实际使用的 `LlmPlanner.decide(ModelTurnRequest)` **每轮只取一个下一步动作，并携带已有工具观察**。保留的旧重载可以解析最多 8 步，但不能据此把现行兼容路径描述为一次性批量计划。对应测试为 [LlmPlannerCompatibilityLoopTest](../matrix-agent-service/src/test/java/com/matrix/agent/model/LlmPlannerCompatibilityLoopTest.java)。
- `PARAMETER` 拒绝允许模型换参重试；`CAPABILITY` 拒绝会阻止本任务后续同能力调用。执行失败也会进入观察反馈，因此已有任务内纠错基础。
- `QQMusicWorkflowGateway` / `BilibiliTitleGateway` 把**新内容理解交给配置模型**，对真实候选展示、明确选择、取消和确认作确定性处理，仍经 Engine 的策略、工具和回读链路。
- 工作流支持依赖、并行只读步骤、有界重试和独立交付状态；拓扑与能力由宿主模板定义，模型不能动态增加边或权限。

**缺口**：未发现独立的失败反思服务、经过验证的跨任务教训复用或动态计划生成/重规划机制。固定 DAG 和较长运行时间本身不证明动态 plan-execute；没有多 Agent 也不能单独证明任务质量差。

### 3. 四层记忆治理完整，语义泛化与经验复用尚弱

- `MemoryRouter` 先保留最多 3 个 Preference，随后 Working 最多 1 个、Semantic 最多 4 个、Episodic 最多 2 个，再用剩余 Preference 回填。调用方请求最多 8 条，`DefaultPromptBuilder` 最终施加最多 8 条、1,024 UTF-8 字节的投影限制。
- [PromptContextAssembler.appendSkillWithinBudget](../matrix-agent-service/src/main/java/com/matrix/agent/task/prompt/PromptContextAssembler.java) 处理 Skill 竞争：当 `base + skill` 超出 `maxMessageChars`，且去掉记忆后的基础规则与完整 Skill 能放下时，直接删除整段记忆区（包含 `<memory_context>`）。若不能采用这一分支，令 `baseRoom = limit - skill.length()`：当 `baseRoom < min(base.length(), 256)` 时，保留截至 `limit` 的 base，**整个 Skill 被丢弃**；否则把 base 截至 `baseRoom` 后拼接完整 Skill。两种兜底分别优先保留基础文本或 Skill，不能概括为只减少记忆。
- [SemanticMemorySourceImpl](../matrix-agent-service/src/main/java/com/matrix/agent/data/memory/SemanticMemorySourceImpl.java) 使用 CJK 相邻字二元组、Latin 整词匹配、`MemoryKeyCatalog.relevance` 词表相关性和静态 score 排序。**命中 key 权重为 2，命中 value 权重为 1**；不是“Latin 命中统一乘 2”。未接入 embedding。
- [EpisodicMemorySourceImpl](../matrix-agent-service/src/main/java/com/matrix/agent/data/memory/EpisodicMemorySourceImpl.java) 负责读取侧：受显式历史意图门控，按有限能力类别召回，并检查终态与事件结构，保留有界旧格式兼容。写入侧由 [EpisodicSummary.PERSISTED_STATES](../matrix-agent-service/src/main/java/com/matrix/agent/task/persistence/EpisodicSummary.java) 限定 `SUCCEEDED / FAILED`，再由 `RoomMemoryWriter.isSafeEpisodicWrite` 校验终态、版本及允许的 JSON 字段等约束。
- **Semantic/Episodic 只向 prompt 投影安全 key，详情需要调用工具读取**；只有白名单数值偏好和经过校验的 Working 温控状态可直接投影 value。
- 显式偏好/事实保存需要保存意图和同从句 grounding。系统也会自动保存有限的任务事件与核验事实，但没有从任意对话主动提炼长期事实、巩固经验的机制。

**评价边界**：这里的 Semantic 表示长期事实层，不表示已采用向量检索。词面召回是能力限制，但“Android 无向量库”只是原实现注释中的选型理由，不能作为不可突破的技术前提。

**隐私边界**：记忆在本地受控保存，默认 prompt 投影也较严格；工具显式读取的结果仍会经 `ModelSanitizer` 保留语义后进入所选模型。选择云端模型时，不能宣称所有 PII 都不会出设备。

### 4. 附件使用受限文本拼接，没有检索选段

当前附件路径为：

1. 摄取流最多 2 MiB，超过即拒绝；文本 MIME/内容检查后解码。
2. `AttachmentTextExtractor` 保留前 16,000 个 Unicode 字符，超长部分截断，并在保留文本后追加 `…(已截断)` 标记；标记不保留被截断的内容。
3. `AttachmentContextProjector` 用与 Engine 相同的单消息预算净化文本，加入 `<user_provided_document>` 与“资料不是指令”声明。
4. 附件与用户输入拼接后，Engine 再施加单消息限制。

**缺口**：没有切块索引、按问题检索、排序和来源定位。最终模型可见文本并不保证达到 16k，2 MiB 摄取上限也不代表整份文件已被模型理解。

**实施含义**：要回答长文档末尾问题，必须先改变摄取保留策略；对已经截断的 16k 文本再切块无法恢复文末。

### 5. 尚无正文 token 流式，但已有实时阶段与调试过程事件

| 层次 | 当前状态 |
|---|---|
| 用户可见运行阶段 | 已有 `QUEUED / PLANNING / EXECUTING`，由 Engine 真实观测点驱动 |
| 调试过程事件 | 已有订阅与历史回放；开启 `matrix.debugTraceUi` 后，过程卡可在最终助手消息产生前更新 |
| 模型正文逐 token 展示 | 尚未实现：云端读取完整响应，MNN 将 JNI token 回调缓冲后返回 |
| 模型 reasoning 详情 | 部分协议可在整次模型响应返回后提取，例如 `reasoning_content`；不能等同于 token 级实时生成流 |

[ConversationViewModel.mergeDebugEvent](../matrix-agent-launcher/src/main/java/com/matrix/agent/launcher/presentation/ConversationViewModel.java) 将事件挂到本轮 USER 消息，明确支持任务进行中展示。因此“全部终态后回放”不符合实现。

SDK 虽定义 `AgentTaskEvent.TYPE_TEXT_DELTA=2`，仍不等于对话正文流式链路已经接通。[IConversationCallback.onTransientTranscript](../matrix-agent-service-lib/src/main/aidl/com/matrix/agent/api/conversation/IConversationCallback.aidl) 的现有语义是语音会话临时转写，绑定 `voiceSessionId`，不应直接改作模型回复通道。

### 6. 有功能回归和真实模型样本，缺少统一、可重复的质量基准

- 1,516 项 JVM、47 项真机测试是已有完整回归记录，不是本次重跑结果。测试覆盖状态机、协议、权限，也覆盖参数修正、媒体选择、上下文保留和失败反馈等行为；它们不能保证所有真实输入下系统都正确。
- [媒体模型理解验证](verification/media-model-understanding-2026-09-27/README.md) 有真实模型、输入、工具耗时、总耗时和回读证据，也有复验入口。它是有价值的小样本验证，不能描述为“零质量证据”或“无量纲”。
- 尚缺固定数据集、自动评分、重复采样、模型/Prompt 对比、失败归因汇总和版本回归阈值。

**核心缺口**：现在无法从统一报告回答“在约定任务分布上成功率多少、哪些类型失败最多、换模型后是否退化”。这仍是最高优先级。

### 7. Prompt 有防御与迭代记录，缺少实验化度量

- 已有记忆与附件数据边界、摘要前缀、日历文本约束、计划创建授权检查、BV 号约束，以及协议和执行层校验。Prompt 声明是其中一层，不能单独证明注入防御完整或“安全满分”。
- `PromptContextAssembler` 组合基础规则、记忆和选中的 Skill；压缩器保留工具调用及其观察的结构化事务，只对适合的自然语言内容摘要，避免改写未知执行状态。
- Git 提交 `0fe7771` 等包含媒体理解、兼容规划 Schema 与相关 Prompt 的变更，因此“写一次、迭代无痕”不准确。
- `LlmIntentClassifier` 请求 `READ / WRITE / UNKNOWN` 标签，并使用有界缓存和降级；这是短标签输出约束，不代表 API 严格只生成一个 token。

**缺口**：缺少关联 Prompt/Skill 版本、数据集版本和效果指标的实验记录，尚不能量化某次 Prompt 修改的收益与回归。

### 8. 已有模型适配与部署，缺少质量、成本驱动的选型证据

当前有多协议适配、MNN 端侧部署、模型 tokenizer 计数与裁剪、运行资源协调等实现。具体位置需要区分：[OnDeviceModelGateway.trimToBudget](../matrix-agent-service/src/main/java/com/matrix/agent/model/OnDeviceModelGateway.java) 调用 `OnDeviceLlm.countTokens`，计入模板与工具开销，并按完整消息组执行端侧裁剪；`task/token` 的 Tokenizer 在 `AgentEngine` 主循环中用于字符/token 双轨日志统计，未替代字符预算裁决。这不能理解为 `ModelApiClient` 或云端路径已有同样的 tokenizer 裁剪。未发现项目自身的微调/蒸馏训练闭环、同任务模型/量化版本质量对比或按任务动态选择端云模型的机制。

**评价边界**：微调、动态路由不是 Agent 项目的必选项。应先比较任务成功率、延迟、内存和成本，再决定是否需要；不能把“未训练模型”直接等同于“没有智能贡献”。

### 评估结论与投入依据

| 优先关注的缺口 | 应建立的证据 |
|---|---|
| 质量评测闭环 | 固定任务集的结果、重复运行波动、失败归因与版本比较 |
| 记忆与附件检索 | 召回准确率、无关内容误召回、最终回答正确性与来源 |
| 正文流式体验 | 首段可见延迟、完成延迟、取消后的残余事件与协议正确性 |
| 经验复用与长程执行 | 后续任务改善、错误教训率、资源预算、恢复与交付可靠性 |

原稿的扣分分配可理解为上述方向的主观优先级，不作为加一项功能就补回固定分数的公式。确定性确认、事务感知压缩和权限治理是质量基础，应在评测中体现收益。下一阶段以可重复数据修订评价，不承诺 P0 做完就到 7.5 分或全部做完就到 9 分。

## 第二部分：改进计划

> 总原则：复用已有幂等、取消、授权、执行回读和数据清除机制；允许对必要的接口、SDK 契约及存储结构作明确扩展，不预先承诺“零现有文件改动”。下面工期仅为单人实施的粗估，包含相关回归，不是排期承诺；首次可运行原型后再估算。

### P0-1 评测体系（Eval Benchmark）

**实施状态（2026-09-28）**：评测框架、110 条版本化语料（媒体 60 / 计划 30 / 多轮 20）、效果评分与反例测试、离线/真实模型两条 Gradle 入口和默认门禁依赖已落地。确定性模式重复两遍通过。真机保存的 glm-5.3 两种协议配置各重复 110 例两遍：原始目标达成为兼容模式 167/220、原生工具模式 162/220；这是同一模型的双配置，不是双模型。已保存逐例输出、时间与分类，不将 Engine SUCCEEDED 视为目标达成。四类真实基线暴露的禁止操作已加入 Host 拦截与确定性重放；其余时间参数等质量失败仍保留。归因 v2 区分参数拒绝与能力拒绝，原 v1 报告不重写。真机真实外部 App 的 9/9 抽样单独统计。见 [evaluation.md](evaluation.md)、[原基线记录](verification/agent-evaluation-2026-09-27/README.md)与[全部实施记录](智能层实施记录-2026-09-27.md)。

**回归发现并修复**：可选歌手/歌名空字符串与 Schema 校验契约不一致；明确“先搜索/先确认”仍可误恢复当前队列；跨应用搜索被播放切换前置条件误拦截，并误选播放来源切换 Skill。Schema 以显式 `minLength=0` 局部允许空实体，默认非空约束保持；目标搜索与播放切换分别判定。真机还发现原 debug 广播探针无法承载慢模型请求，长操作已转移到不导出的 debug 前台服务，入口继续受 DUMP 权限保护。

**目标**：建立后续改进可共用的质量基线，区分模型理解、策略拦截、工具执行和用户目标达成。

**方案**：

1. 新增 `matrix-agent-service/src/test/java/com/matrix/agent/evaluation/` 和版本化用例资产。用例至少包含 `id / tags / turns / fixtures / expect / scoringVersion`；多轮通过 `turns` 表示，fixtures 定义候选、时间、时区和 Provider 状态。期望结果包括允许的动作或澄清、禁止的写操作、参数匹配及最终效果，不强迫所有正确实现采用唯一工具序列。
2. 首批目标仍为媒体 60 条、计划 30 条、多轮确认 20 条，明确去重与统计分母。覆盖实体歧义、否定、候选过期、BV、计划授权词、时间歧义和跨轮状态。合理澄清是有效结果，不能一律算失败。
3. 分开运行并标注环境：
   - **确定性回归，CI 必跑**：脚本化 `ModelGateway` + 假 Provider，检查策略和编排。现有 `DemoModelGateway` 不具备完整媒体搜索、计划决策，不能直接承担整套用例。
   - **真实模型评测，本地显式运行**：真实网关 + 固定 Provider fixtures，评估模型在受控环境中的决策。使用本地或远端实际模型；MockWebServer 只用于协议回归，不能替代质量评测。
   - **真机端到端抽样**：单独统计真实 App 页面、搜索和回读成功率，避免把假 Provider 的结果称为真实播放成功率。
4. 复用 `PolicyEngine`、`CapabilityRegistry`、`ModelApiClient` 与现有 JVM 测试装配。相关类仍涉及 Android 日志/平台边界，应使用 Android 模块已有测试配置，不能称为完全无 Android 依赖的纯 Java 程序。
5. 报告记录 commit、用例/Prompt/Skill 版本或哈希、模型与协议、解码参数、运行次数、随机性配置、任务预算和 fixture 版本。分别输出目标达成率、正确澄清/拒绝率、越权或误执行率、延迟及可取得的调用量/成本；无法取得的 usage 标为未知。
6. 失败归因包括 `TOOL_ARGS_WRONG / CANDIDATE_MISS / POLICY_OVERBLOCK / POLICY_UNDERBLOCK / PROTOCOL_ERROR / TIMEOUT / PROVIDER_FAILURE / GOAL_NOT_MET / UNKNOWN`，允许主因与次因。区分模型建议和实际执行，证据不足时保留 UNKNOWN。

**关键约束**：不能把 `TaskState.SUCCEEDED` 直接当作用户目标达成。Engine 在正常结束且没有工具调用时也可能返回该状态；评分必须检查期望答复、必要澄清或可验证的执行效果。字符串匹配适用于固定协议结果，开放文本需有明确评分规则和人工抽检。

**涉及入口**：新增评测包与资源、模块 Gradle 任务、根 `verifyArchitecture` 的确定性依赖；复用现有注入接口，必要的可测性调整单独评审。用例只含合成数据，测试报告不得包含凭据。

**已实现命令**：

```sh
./gradlew :matrix-agent-service:runEvaluations
./gradlew :matrix-agent-service:runModelEvaluations -Pmodel.config=/path/to/local-config
```

真实模型任务不进入默认架构门禁；本机配置放在已忽略的 `.model-evaluation/`，报告在模块 `build/reports/evaluations/`；固定用例和评分规则随源码维护，配置示例仅引用凭据环境变量。

**验收**：同一数据集可重复执行；确定性模式无网络、无模型费用；真实模式至少对两个模型配置重复采样并输出逐例结果、分类汇总和差异。冻结基线后制定回归阈值，禁止操作用例出现实际违规执行必须阻断回归。

**粗估**：1～2 周完成首批可用基线；真实 App 端到端自动化扩展另估。

### P0-2 失败反思与受控教训复用

**实施状态（2026-09-28）**：已实现结构化证据投影、固定教训码、独立 v17 表、owner/zone/epoch/TTL 与去重、异步 8 秒 deadline、清除/关闭围栏和受预算限制的召回。真实 A/B 已完成 16 次案例：OFF 5/8、ON 4/8，越权均 0；3 次合格反思调用均因格式或超时失败而回退 UNKNOWN，0 条有效教训，不能将开关差异归因于学习。生产默认关闭，只有稳定收益证据才调整开关。没有扩大 Episodic 原白名单，也不把模型推测写成用户事实。

**目标**：先验证反思是否改善后续任务，再扩大自动经验写入；模型推测不直接升级为用户事实或授权。

**必须先解决的现状约束**：

- Episodic 钩子在 `AgentEngine` 的终态出口，经 `TaskMemoryWriter → EpisodicMemorySink` 写入，不在原稿所称的 Repository 摘要挂接点。
- `EpisodicSummary` / `RoomMemoryWriter` 只接受 `SUCCEEDED / FAILED`；JSON 字段白名单仅允许 10 个固定字段，事件类别与核验事实也有校验。增加 `lesson` 字段或 `failure_lesson` 枚举不能自动通过现有写入、读取与投影。
- Episodic 召回要求历史意图，Semantic/Episodic 正文不直接进 prompt。“再说一次同意图请求”不保证召回上次教训。
- `AuditRedactor.redactFreeText` 将自由文本变成长度及摘要标识，可能已移除分析实体歧义所需的语义；`redact` 仅做凭据替换和截断，也不能直接充当任意自由文本的完整 PII 过滤器。

**方案**：

1. 先用 P0-1 的合成失败轨迹验证诊断价值。歌手歧义本身不算失败，合理澄清应通过；选择可复现的错误参数、漏掉必要前置读取等案例，并设置无需反思的确定性基线。
2. 新建异步 `FailureReflectionService`，由 task 终态出站端口装配触发，仅处理明确选择的 `FAILED / PARTIALLY_SUCCEEDED` 类型。参考 `ConversationTitleService` 的轻量调用方式，增加有界队列、独立 deadline、去重、关闭与清除后丢弃规则；失败不改变主任务终态。
3. 输入仅取审计安全的结构化投影，例如能力名、拒绝类型、状态、StopReason、核验标志和受限证据引用。禁止直接传 `internalResults` 或恢复用户原文；不能归因的样本返回 UNKNOWN，不编造失败原因。
4. 首版输出采用有版本的 `category / lessonCode / evidenceRefs` 白名单，由 Host 校验并生成固定说明。定义独立的 FailureLesson 记录及记忆域读写端口，不混入用于用户显式保存事实的 `fact.*`。存储实现须明确 owner/zone、来源任务、epoch、TTL、去重和删除规则，所需迁移纳入实施范围。
5. 增加独立、受预算限制的教训召回与 prompt 投影，按能力/失败类别等受控信号匹配，不依赖“上次”字样。标注为可参考的诊断建议，不改变工具、权限、保存准入或策略拒绝结论。

**验收**：对预先冻结的重复任务集比较开启/关闭反思的后续目标达成率、额外延迟和错误教训率；覆盖跨用户/音区隔离、清除竞态、重复终态、模型失败和无证据归因。“prompt 出现 lesson”只是连通性检查，不是收益验收。没有观察到稳定收益时不默认启用。

**依赖与粗估**：依赖 P0-1 的失败基线；诊断原型约 3～5 天，完整闭环（含原型、生产存储、召回和回归）约 1～2 周，原型后重新估算。

### P1-3 正文 Token 流式输出

**实施状态（2026-09-28）**：已接入 OpenAI/Anthropic/Gemini SSE、MNN 原生回调、Engine/装饰器/SDK 15/Launcher。云端 glm-5.3 与端侧 Qwen3-0.6B 真机流式及首片段取消通过；云端 UI 捕获到逐步增长的正文，Host 与 Launcher 重启后恢复同一最终消息。其他云协议由解析与真实本地 HTTP 边界测试覆盖；Ollama 保留非流式回退。模型出口 TTFT 与屏幕采样延迟分别报告。

**目标**：降低正文首次可见等待，同时保留完整轮次校验、取消和终态事实语义。

**方案**：

1. 扩展 `ModelGateway` 的流式处理接口，并同时接入 `prepare` / `ModelCallExecutor`、执行 lane 和媒体网关装饰器；默认实现保留非流式兼容。定义正文、工具参数片段和完成/错误事件的区别。
2. 为 OpenAI、Anthropic、Gemini 分别实现协议解析；若首期不覆盖 Ollama 原生协议，明确其仍回退非流式。复用 HTTP 客户端、abort-hook 与响应大小约束，但 `JsonHttpTransport.post` 当前是整段 JSON 读取，需要新的流式读取实现。
3. MNN 透出 token 回调时增加增量解析与缓存边界，区分正文、工具调用标签和推理片段；工具参数须完整、校验成功后才执行。公开正文不混入原始推理和工具 JSON，已有调试通道继续独立管理。
4. 经 task 出站端口、`ConversationTaskProgressBridge` 和 Coordinator 建立明确的 assistant 临时输出事件。事件携带任务/轮次关联与序号，处理重复、迟到、重试、取消和终态清理。**不复用语音 `onTransientTranscript` 的语义**；新增 SDK/AIDL 契约时完成版本与 contract-hash 协商检查。
5. 对 Binder 事件限幅、合并和节流，UI 暂存正文；最终回复仍以 `writeTerminal` 及现有终态投影为权威。取消、协议损坏或截断时不得把已展示片段误认为完整成功答复；断连后以已持久化消息恢复。
6. 明确首个片段发出后的重试规则，禁止透明重试造成文本重复或工具重复执行。deadline 仍约束完整调用，不因持续收到片段无限延长。

**验收**：云端和 MNN 各完成正文流式链路；覆盖 UTF-8/标签/JSON 跨片段、EOF、截断、取消、迟到事件和异常重试；统计首次可见延迟、最终延迟、事件量和取消后残余输出。非流式旧路径与最终消息恢复语义回归通过。

**涉及入口与粗估**：模型/transport、task 端口、conversation、SDK 和 Launcher；约 2～3 周，具体协议覆盖范围在首个端到端原型后确定。消息表可争取不改，但不能据此承诺契约和恢复逻辑零改动。

### P1-4 端侧语义记忆（embedding 混合召回）

**实施状态（2026-09-28）**：已实现 BGE/MNN 512 维、v18 派生索引与 CAS/回填、0.50 阈值和 RRF 融合、投影统计及无模型降级。固定查询集的应用内保留集 Recall@5 为词面 3/12、向量 8/12、混合 10/12，各 6 条负例误召回均为 0。已支持通过构建参数携带固定制品，首次使用经生产安装器校验后原子安装；真机独立空目录安装并编码约 1.3 秒。不携带且未安装模型时仍为词面检索。真实回答对照使用“正确陈述＋实际读取对应事实”的评分，不把拒答中的候选词算成功；见实施记录。

**目标**：先提升 Semantic 事实的同义表达召回；embedding 计算留在设备上，保持现有保存准入和模型数据投影边界。Episodic 不因这一项自动完成语义检索升级。

**现状约束**：召回成功不保证记忆进入最终 prompt。`PromptContextAssembler.appendSkillWithinBudget` 在上述预算竞争分支会整段移除记忆区；即使 embedding 命中正确记录，其安全 key 也可能未传给模型。极小预算分支下，Skill 也会被整体丢弃；另一兜底分支则保留完整 Skill 并截断基础文本。评测必须区分检索未命中、记忆或 Skill 被预算移除、模型未取值和回答错误，不能把这些失败统一归到检索算法。

**方案**：

1. 先做中文小 embedding 模型的端侧适配试验，验证转换、tokenizer、pooling、归一化、输出维度、内存、冷启动和耗时。bge-small-zh 等仅作候选；模型大小、维度和真机性能由实际制品确定，不预设“512 维”或“<10ms”。
2. `ondevice` 增加 `OnDeviceEmbedder`，明确生命周期、串行/资源协调和取消边界。模型目录、校验和、临时下载与原子安装流程可复用，但需验证新的模型类型及运行配置。
3. 当前 Semantic 上限是每个用户/音区该层 1,024 条，Preference 也有独立配额，不是所有层合计 1,024 条。可先采用有界内存余弦扫描；内存与时延需同时测查询编码、数据库加载和相似度计算。
4. 索引除向量外，保存模型/索引版本、维度及 value 版本或摘要。**推理在数据库事务外完成**，再于事务内核验身份、epoch 和对应 value 后提交；异步补算不能把旧 value 的向量覆盖到新值上。设计旧记录回填、模型切换重建和无有效向量时的降级。
5. 比较词面、纯向量、混合召回；关键词累计分与余弦分不在同一尺度，先归一化或采用可解释的排名融合，再通过评测选择阈值与权重，不直接使用未经标定的 `max(关键词分, 余弦×w)`。
6. 保存仍要求显式意图和 grounding；默认 prompt 仍只投影 Semantic key，详情通过原工具读取。分别评估“召回命中”“安全 key 是否保留在最终 prompt”“模型是否正确取值”“最终回答正确”，同时检查选中的 Skill 是否完整进入最终 prompt，记录 Skill 与记忆竞争时的预算裁决。若调整预算分配策略，另验基础规则和完整 Skill 的保留，不以向量命中为由自动放宽约束。本地 embedding 不代表后续云端模型调用没有数据外发。

**验收**：

- 对冻结的同义改写和困难负例集报告 Recall@k、无关记忆误召回、记忆投影保留率（已召回且可投影的条目中，安全 key 实际进入最终 prompt 的比例）、记忆区整段移除率，以及 **Skill 投影保留率**（已选出非空 Skill 文本的请求中，该文本完整进入最终 prompt 的比例；无 Skill 请求不计入分母）。同时报告端到端回答正确率、延迟与峰值内存。
- 覆盖无 Skill、带 Skill、整段记忆移除、保留 Skill 并截断 base、极小预算丢弃 Skill 的场景，检查 `baseRoom` 阈值两侧及等值情况，并按场景分别统计，证明检索收益在实际装配后仍成立。
- 模型未下载/损坏/版本不符时退回现有词面路径；覆盖更新、删除、清除与回填竞态。不能只选词表已经直接命中的例子证明提升。

**依赖与粗估**：P0-1 评测及端侧适配试验；约 2～3 周，模型转换与设备兼容风险需先验证。迁移编号在合并时按数据库实际版本分配，不提前占用 v17。

### P2-5 附件 RAG（完整摄取、切块与相关性选取）

**实施状态（2026-09-28）**：已实现完整 UTF-8 有界摄取、v19 分块/索引/提交期来源冻结、BM25/CJK 二元组检索及 SDK/UI 范围展示。真机文末、跨块、多附件、无证据、注入五类模型问答通过；真实 UI 从 31,279 字文件尾部取回口令/日期并显示 [a1-c47] 原文位置。空管道取消、删除/清除、坏 UTF-8 和索引清理通过。首版为 BM25，附件向量增强仍属后续可选比较，不把语义记忆向量自动视作附件向量检索。

**目标**：在有界摄取和上下文预算内保留长文档可检索性，让回答能定位依据。

**方案**：

1. 先改摄取策略：在现有字节/MIME 边界内保留可索引全文，或摄取时直接生成有界块集，避免先丢掉 16k 之后的内容。明确总块数、总存储量、清理和取消上限。
2. 以约 800 字、15% 重叠作为待评测初值，并尽量保留段落边界。块存储带附件 ID、块 ID、字符区间和内容版本；可扩展现有附件表或引入子表，迁移编号随实际版本确定。
3. **先建立 BM25 词面基线，不硬性依赖 P1-4**。CJK 二元组分词可以复用思路，但现有记忆打分不是完整 BM25，还需词频、文档频率与长度归一化。端侧 embedder 可用后再对比混合检索。
4. 在提交期用用户原始问题检索 top-k 块，控制片段总预算（初值 4k 字符），为问题、标签和来源预留空间；仍使用“资料不是指令”边界，避免之后的 8k 单消息限制破坏所选片段。
5. UI 展示实际引用的块/段落位置和覆盖范围，不能仅凭 `selectedChars/totalChars` 宣称用户知道引用了哪部分；无相关证据时应说明未找到依据。

**验收**：超过 16k 的文末问答、跨块问题、多附件检索、无相关内容和附件注入用例均有基线；报告片段召回、回答准确率、来源定位准确率、上下文占用与耗时。附件删除、用户清除、摄取失败时不存在残留索引。

**依赖与粗估**：P0-1；BM25 首版约 1～2 周，向量增强可后续接入，取决于 P1-4。不能把摄取、存储、引用和回归都缩减为投影器的 3～5 天修改。

### P2-6 长程任务模式（research profile）

**实施状态（2026-09-28）**：已贯通 Host RESEARCH、父级 30 分钟活动/40 次模型/40 次工具预算、单步 180 秒、40 分钟到期窗口、v20 模型账本、固定八步图及版本化只读检查点。受控 web.search 仅访问 Wikipedia/Crossref/arXiv，片段与书目不冒称全文。真实多源任务已交付；逐秒确认 90 秒进程停机后的恢复运行以 183.282 秒活动账本完成并交付（保守账本含恢复时段，不冒称连续推理）。进程恢复、用户交互抢占、取消/撤销/到期及耗尽预算分别留存 run/step 报告。普通交互与普通定时 AGENT 仍用原预算。动态计划和通用浏览器不属于该首版。

**目标**：先证明有界、可取消、可恢复的长任务承载能力，再单独评估动态计划与重规划是否必要。

**现有约束必须一起检查**：

| 层次 | 当前约束 |
|---|---|
| Engine | 默认 8 次迭代、8 次工具调用，以及字符/消息数预算；实例预算由装配注入 |
| 自动执行入口 | 普通定时 AGENT 执行路径有 60 秒预算装配，位于 [ScheduledExecutionGraph](../matrix-agent-service/src/main/java/com/matrix/agent/host/di/ScheduledExecutionGraph.java) 的 `ExecutionScope` 与 `PreparedAutomaticTask` 构造处 |
| 工作流活跃预算 | `ActiveBudget.allowance` 限父级活跃时间 120 秒、单步最多 60 秒 |
| 模板 | `WorkflowTemplate` 最多 8 步，单步 timeout 最大 60 秒；仅只读步骤允许配置 0～2 次重试，非只读步骤的 `maxRetries` 强制为 0 |
| 工具累计量 | `WorkflowExecutionGraph` 的父 run 工具调用最多 16 次 |
| 到期与授权 | allowance 还受 `expiresAt` 和执行范围约束；默认 grace 为 10 分钟，不能放大活跃预算却继续受原到期窗口提前终止 |

**方案**：

1. 设计 Host 控制的 `INTERACTIVE / RESEARCH` profile，同时贯通请求构造、Engine 实例预算、调度预算、到期语义和模板校验。40 次迭代/调用、30 分钟仅作为试验上限，不是默认开放给模型自选的参数。
2. 仍从 schedule 域进入，明确模型 lease、用户交互抢占、CPU/前台服务生命周期、取消与数据清除语义。前台服务是承载机制，不能单凭其存在证明长时间运行或恢复已可靠。
3. 先补受控只读 `web.search` 能力及固定多源检索模板，明确网络授权、域名/重定向处理、响应大小、来源和工具结果边界。搜索结果提供什么证据、是否需要额外正文读取能力应明确，避免用摘要冒充完整资料。
4. 定义安全检查点和重启处理。已核验只读结果可在明确版本与期限下复用；写操作仍遵守幂等、回读和 `EXECUTION_UNKNOWN` 规则，禁止恢复时盲目重放。长程压缩还需处理不断累积的结构化工具事务，不能只同比放大字符阈值。
5. 第一阶段采用 Host 固定模板；若增加动态 plan-execute，另行定义模型计划的 schema、Host 校验、边/能力白名单、重规划触发和检查点协议，并单独评测。

**验收**：用超过现有短任务预算的真实多源任务证明完成与来源正确；另用受控故障验证长时上限、取消、重启、网络失败、授权撤回和交付。报告完整 run/step、耗时、资源/调用消耗与恢复行为；任务耗时更长本身不算智能收益。

**依赖与粗估**：P0-1、搜索能力及长程恢复设计；固定模板承载首版约 2～4 周，动态计划/重规划另估。

| 优先级 | 项目 | 粗估 | 依赖与推进条件 | 首要收益指标 |
|:---:|---|---|---|---|
| P0 | 评测体系 | 1～2 周 | 先冻结合成用例与评分口径 | 可重复目标达成率与失败分布 |

## 附：实施与验证约束

1. **合成数据与结果分域**：真实模型评测可能产生费用并向 provider 发送请求，只使用合成输入；fixtures、评分器和报告与生产数据分开。诊断报告不包含凭据，是否保留原始合成响应需明确大小和生命周期。
2. **反思的事实边界**：`Trajectory` 可作为安全投影来源，但不能假设其保留完整语义；反思不读取 `internalResults`，不把猜测当成核验事实，不改变策略与授权。输出缺少证据就记录 UNKNOWN。
3. **流式的终态边界**：临时正文不能替代最终消息事实；复用“终态持久化”的原则，不混用语音转写契约。协议、SDK、取消、重试与恢复回归都属于实施范围。
4. **派生数据一致性**：embedding 在事务外推理，在事务内校验 epoch 和内容版本后提交。删除、清除、模型切换、附件失败及异步回填都必须处理派生数据，不能形成旁路残留。
5. **迁移与契约版本**：审阅基线的 `MatrixDatabase` 为 16；本次按实际实施顺序迁移至 20（17 教训、18 向量、19 附件块、20 研究模型账本），schema fixtures 与独立旧库 16→20 验证已更新。新增 AIDL/DTO 按既有版本和契约检查流程推进。
6. **验证记录**：`verifyArchitecture` 接入确定性回归；真实模型和真机验证显式运行，并在 `docs/verification/<feature>-<date>/` 记录模型、协议、环境、样本和边界。历史 1,516/47 的结果不自动覆盖新功能。
7. **评价纪律**：质量提升由同一基准的前后对照支持。增加 embedding、反思、流式或更多迭代次数都不自动获得固定分数；正确澄清、拒绝越权和如实表达未知结果也属于成功行为。
