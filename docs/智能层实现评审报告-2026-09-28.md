## 第一部分：问题清单（按严重度）

### 高（1 项）

**H1 · 研究任务 summary 提示词可超上限，整 run 在最后阶段失败且原因误记**

- 位置：`ResearchWorkflow.goal`（ResearchWorkflow.java:93-124）、`PreparedAutomaticTask`（PreparedAutomaticTask.java:12-15）、`quoted()`（ResearchWorkflow.java:150-153）
- 事实：goal() 构造 summary 提示词无总长预算。按各字段上限计算（6 命中 × id 20 + 标题 ≤60 + 片段 ≤300 + 元数据，3 条 review 引用 × ≤400，查询 300，固定说明 147）可达 **4,198 字符 > 4,096 上限**；且 `quoted()` 的 HTML 转义发生在截断**之后**，`&`→`&amp;` 可再膨胀数倍，实际触发门槛更低。
- 触发场景：三站点全部成功、每站 2 条命中接近标题/片段上限、三条 review 接近 400 字（提示词允许 ≤600 字，常态可达）。
- 后果链：构造器抛 `IllegalArgumentException` → 兜底 catch（WorkflowExecutionGraph.java:197-199）→ summary 步 FAILED、reason 误记 `STEP_EXECUTION_INTERRUPTED` → summary 为必需步 → **整 run FAILED**，此前检索/分析预算全部作废。fail-closed（无错误交付）成立，但属运行级失败。
- 修复方向：在 `goal()` 对**转义后的完整提示词**同时施加字符与 UTF-8 字节预算，按来源公平压缩 snippet/review 且保留至少两个站点的可引用证据；用专门的超长 reason 区分于执行中断。单独放宽 `PreparedAutomaticTask` 的字符上限不能保证其 8 KiB 字节上限，也不能保证提示词仍在模型上下文预算内。

### Major（4 项，合入/最终验收前处理）

**M1 · 四条新数据库迁移（16→17→18→19→20）缺逐版本回归测试**

- 位置：`MatrixDatabaseMigrationTest.java` 的独立目标版本仅 {2,5,6,8,9,10,11,12,13,14}；四条新迁移在 test/androidTest 中均无逐版本用例。debug `IntelligenceDeviceProbe.migration`（:84-115）另有 v16→v20 合成库升级检查。
- 已有验证：DDL 与 schemas/17–20.json 已人工比对；Mi 9 SE 上用 schema 16 建立隔离 SQLite 库、写入旧记录、经 Room 连续迁到 v20，版本/原记录/外键检查均通过（`docs/verification/intelligence-2026-09-27/intelligence-device.json` 的 `legacy_room_migrations`）。因此不能说“完全没有迁移验证”。
- 仍缺：这个一次性的真机链路探针没有分别固定 16→17、17→18、18→19、19→20 的目标 schema、索引、列属性和真实历史数据夹具；不进入常规 `androidTest` 回归门禁。“每迁移有测试”仍未满足。既有 v15、v16 迁移也有相同缺口。

**M2 · 启动必需的 embedding 清单未被 Git 跟踪，遗漏提交会导致启动失败**

- 位置：`src/main/assets/embedding/bge-small-zh-v1.5.json` 与 `NOTICE.txt` 当前均为 untracked；`EmbeddingRuntimeGraph.java:30-36` 在容器初始化时无条件打开清单。`NOTICE.txt` 用于制品归属说明，**不是**启动必读文件。
- 触发场景：若提交遗漏清单，CI 从该提交构建可通过编译，但任意变体（含 release）启动时抛 `IllegalStateException`；遗漏 NOTICE 不会造成同一启动崩溃。缺权重文件则是运行时向词面召回降级，与缺清单不同。
- 处理：有针对性地暂存并核对清单与 NOTICE；检查暂存区文件清单，构建门禁增加清单存在性断言。不要用无差别 `git add -A` 代替暂存审查。

**M3 · 评测证据链版本脱钩：v2 已执行，但归档仍是旧代码报告**

- 位置：归档 `docs/verification/agent-evaluation-2026-09-27/offline-report.json`；当前运行产物 `matrix-agent-service/build/reports/evaluations/offline/report.json`。
- 事实：归档的 `evaluatorSourceSha256=1dc338a0…`、`productionSourceSha256=4cb574dd…`，与当前产物的 `838f52a1…`、`5c775e41…` 不同，语料哈希相同。归档无 `attributionVersion`；2026-09-28 复跑门禁生成的当前报告为 `evidence-v2`、`complete=true`、`repetitions=2`。因此“v2 从未执行”不成立，准确缺口是**已执行但未归档**。另存的真机 `real-model-report.json` 仍是 original-v1；summary 明示 `newImplementationCovered=false`。
- 后果与处理：审计者无法仅凭归档重放当前确定性归因，也不能把旧真实模型基线当作新实现的质量结果。归档当前哈希的 v2 离线报告，并在真机评测器补齐元数据后为新实现建立单独的真实模型基线。

**M4 · 真机评测报告缺计划要求的元数据**

- 位置：`DeviceEvaluationRunner.java:33-41`
- 事实：当前 `DeviceEvaluationRunner` 已写 `attributionVersion`，以及 corpus/Skill 哈希、评分/夹具版本、重复次数；但缺 commit、工作区状态、预算、实际解码参数和请求测量。`ModelApiClient` 使用容器共享 client，未接入评测专用的 `HttpMeasurements`；旧报告的 commit 只由外部 summary 事后补记。
- 后果：真机报告自身不足以证明两次运行的代码与解码配置可比；旧真机报告又标明未覆盖当前实现。补字段与采样后需重新运行，不能只改旧报告的元数据。

### 中（5 项；沿用原编号）

**Z1 · 显式 JSON null 的 finish/stop_reason 处理在测试与生产环境分叉，且两条路径都整轮失败**（P1-3）

- 位置：`StreamingToolProtocol.java:142`（Anthropic）、`:188-190`（Gemini）
- 事实：`optString(key, fallback)` 对显式 null 的语义：JVM 测试用 org.json:20240303 返回 fallback，Android libcore 会把 `JSONObject.NULL` 转成字符串 `"null"`。Anthropic 兼容端点在 `message_delta` 发 `"stop_reason":null` → JVM 侧报 incomplete / Android 侧 `PROTOCOL_ERROR`；Gemini 兼容端点中间 chunk 发 `"finishReason":null` → Android 侧 `complete=true` 提前截断流。已有 GLM 真机样本未触发；跨环境语义分叉仍需用两套运行时的回归测试固定。
- 修复：改用 `isNull()` 守卫读取。

**Z3 · embedding 首次安装与编码共用 2 秒等待上限，慢设备可能持续无法启用向量召回**（P1-4，风险推演）

- 位置：`EmbeddingRuntimeGraph.java:78` `work.get(2, TimeUnit.SECONDS)`；安装路径 `EmbeddingArtifact.java:61-94`
- 代码事实：2 秒上限包含 modelExecutor 排队、首次约 37 MB 资产复制、SHA-256 校验、模型加载与编码；超时后 `abandoned` 使进行中的安装在取消检查点退出并清理 staging。安装异常设 30 秒退避；任务若尚未开始就被取消，则不会产生该次安装 IO。真机首次安装加编码用时 1,308ms，仅证明该设备达标。
- 待验证风险：如果目标设备每次安装加加载都超过 2 秒，重复请求可能反复中止并退避；首次调用恰与长时间 MNN 生成争用同一 lane，也可能先在队列中超时。尚无慢设备复现或周期性 IO 的测量，不能写成已发生或无条件“永远失败”。建议把安装准备与单次编码等待预算分开，并在目标设备记录首次/竞争时延。

**Z4 · HYBRID/VECTOR 融合分支零确定性 JVM 覆盖**（P1-4）

- 位置：`SemanticMemorySourceImpl.java:99-118`（RRF 融合、VECTOR 空结果短路、fail-open）
- 事实：test 源码集 grep `Mode.HYBRID|Mode.VECTOR|SemanticVectorRecall` 为 0 命中；`SemanticMemorySourceImplTest` 全部走 2 参 LEXICAL 构造。唯一覆盖是真机探针一次性运行。融合排序/短路/fail-open 是纯 Java 逻辑，完全可用 fake recaller 做确定性回归——与附约束 6"`verifyArchitecture` 接入确定性回归"有差距。

**Z6 · BM25 每次提交对全部候选块重分词，大附件的提交时延缺上限实测**（P2-5，风险推演）

- 位置：`Bm25Retriever.java:23-31` + `ConversationAttachmentPort.retrieve`（submitText 的 Binder 线程同步执行）
- 代码事实：非 overview 查询对加载的全部块重新生成词项并计算 BM25，处于提交路径；单次最多 4 个附件、每个源文件最多 2 MiB UTF-8。四份全中文文件约 280 万汉字；按无段尾吸附的 800 字/重叠 120 字切分，约 **4,112 块**，有段尾吸附时数量会增加。原“12k+ 块”把字节、字符和切块步长混用了。
- 性能边界：已保存的 26k 字、80–126ms 真机样本不能直接证明最大语料耗时 8–14 秒；该数字只能作为线性外推，且分词分配、数据库读取、GC 不一定线性。建议先测最大允许的中文/英文/段落密集样本与 Binder 占用，再决定缓存词项或限制参与打分的语料，并显式标出降级覆盖范围。

**Z7 · `ReadTransactionCompactor` 在当前发布图中不可达，实施记录描述与实际不符**（P2-6）

- 位置：研究 AGENT 步 scope 能力集为 `Set.of()`（WorkflowExecutionGraph.java:213）；`verifiedReadTool` 仅在 `AgentEngine` 回路产生（AgentEngine.java:666）；压缩器接线在 ConversationCompressor.java:124-126
- 事实：`PolicyEngine` 第一行即拒绝一切工具调用，web.search 的 TOOL 步走 `AutomaticTaskExecutor.tool` 不经引擎会话——RESEARCH 引擎会话中不可能出现已核验 web.search 事务，压缩器当前是死接线（仅单测可达）。机制本身经验证正确（`verifiedReadTool` 仅 Host 置位、文本伪造不可压缩、写/未知/不完整事务原样保留）。**实施记录第 23 行把它描述为 RESEARCH 现行行为，与实际不符。**
- 处理：修正文档标注"为未来允许工具的 RESEARCH 引擎步预留"，或调整接线。

### 原评审误判，已撤回（不计入问题数）

- **Z2（SSE EOF 派发）**：[WHATWG 的事件流解析规范](https://html.spec.whatwg.org/multipage/server-sent-events.html#interpreting-an-event-stream)要求 EOF 丢弃未遇空行的 pending data；单个尾随换行的 `data: [DONE]\n` 仍不是完整事件。`SseHttpTransport.read` 在没有显式完成信号时报告 EOF，方向正确。若将来为非规范 provider 做兼容，应单列互操作性取舍，不能称为 SSE 合规修复。
- **Z5（FileInputStream 终结器误关 fd）**：[Android 35 的 FileInputStream.getChannel](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/refs/heads/androidx-constraintlayout-release/android-35/java/io/FileInputStream.java)把 `this` 传给 [FileChannelImpl.parent](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/refs/heads/androidx-constraintlayout-release/android-35/sun/nio/ch/FileChannelImpl.java)，channel 持有父流的强引用，关闭 channel 时也关闭父流。`AttachmentInputStream.close` 随后关闭 PFD。原报告“临时流立即可回收、终结器误关复用 fd”的因果链不成立；可以为了所有权可读性重构，但不是该故障的修复。
- **Z8（主模型不检查网络授权）**：`ModelCallExecutor.decide`（:104-110）在网络执行 lane 且 `networkAllowed=false` 时明确拒绝主模型调用；`LlmModelGateway` 使用默认 NETWORK lane。`TaskRuntimeGraph`（:67-68）对端侧 gateway 不装配 `LlmSummaryProvider`。因此不存在报告所称“主模型可联网、唯独压缩被禁”的既有定时任务质量回归。`LlmSummaryProvider` 的额外检查是防御边界。
- **L39（BM25 块数上限靠隐式算术）**：`DocumentChunker.MAX_CHUNKS=4096` 在切块时显式检查，`Bm25Retriever.rank` 又直接以 `4 * DocumentChunker.MAX_CHUNKS` 检查候选块数。上调 2 MiB 输入上限不会使检索器的限制因“约 3,082 块”计算失效；若文本超出切块上限，会先在切块阶段明确失败。
