# Agent 当前位置天气简报与定时任务扩展专题

> 版本：v0.2 · 2026-10-06<br>
> 状态：**核心代码已实施并进入设备认证；当前位置定时模式在当前 ROM 上暂不开放，真实天气 API 尚待项目凭据验证**。详见 §12。<br>
> 基线：当前仓库 `main`，MatrixAgent 0.7.2、Room schema 20；延续[定时任务与子任务编排专题](Agent定时任务与子任务编排专题.md)和[实施记录](Agent定时任务实施记录.md)。<br>
> 目标设备：Mi 9 SE / LineageOS 22.2 / Android 15，Host 为平台签名、system UID，targetSdk 36。该部署身份不作为绕过 Android 定位授权与后台限制的设计依据。

## 1. 目标与当前事实

用户示例：“那制定每天九点十分的闹钟，并告诉我当天的天气情况”。希望每天到点，获得**当时所在城市**的天气，而非创建计划时所在城市的长期天气。对这个目标，Agent 应拥有计划、位置解析、天气查询和交付的完整运行事实；DeskClock 标准 `ACTION_SET_ALARM` 只有委托结果，没有可关联的响铃回调及稳定创建回执，不能用作天气工作流的父任务。

2026-10-06 09:03 的设备日志显示，该示例的实际失败链为：意图分类模型超时 → 关键词回退因“告诉我”把混合请求标为只读 → `clock.set_alarm` 与 `schedule.create` 先后被 `PolicyEngine` 拦截 → 后续模型轮次耗尽 60 秒。两次工具调用均无成功效果；界面“任务超时”只是最终表现。即使解除只读误判，现有 `ExplicitScheduleIntent` 对每日钟点只识别 `HH:mm`，不能核验“九点十分”；现有 `web.search` 只覆盖 Wikipedia、Crossref 和 arXiv 的受限研究检索，不是天气数据源。修复这些入口缺口属于本专题的一部分，不能只接一个天气 HTTP API。

现有可复用边界：`ScheduleStore` 的重复发生与去重、`WorkflowCatalog` 的冻结模板、`WorkflowStore` 的父预算/步骤事实、`ExecutionScope` 的能力/网络授权、`CapabilityRegistry → PolicyEngine → ToolExecutor`、`MatrixHttpClient` 的进程级客户端，以及任务中心和通知回执。Host 和 Launcher 目前均未声明定位权限，也没有已注册的当前位置能力。现有本地提醒冷路径只负责受理和通知；不能为了天气把定位与网络请求放进接收器。

### 1.1 本专题交付目标

1. 用户可创建“每天 09:10 按当前位置获取当天预报并提醒”的 Agent 计划；计划页明确显示它**不是 DeskClock 原生闹钟**。
2. 每次发生时重新确定位置、归属城市与当地日期，再获取该城市天气；位置与天气的时效、来源和失败原因可核对。
3. 到点提醒与天气内容解耦：天气或定位失败不能让用户误以为定时触发根本没有发生。
4. 定位、联网、可选播报分别取得并持久化最小授权；权限撤销后安全降级，不用 system UID 静默扩大能力。
5. 不伪造天气，不把旧城市、过期观测或预报说成“当前位置实时天气”。

### 1.2 不纳入本期

- 不改造 DeskClock 私有数据库，不承诺与原生闹钟列表、响铃声或关机闹钟等价。
- 不接入路线、交通、灾害预警、空气质量、任意天气网页抓取或模型自行选择数据源。
- 不持续追踪位置，不记录轨迹；不要求后台常驻 GPS。
- 不允许天气响应正文改变计划、调用工具、扩大网络域名或发送外部消息。

## 2. 推荐裁决

| 编号 | 推荐决定 | 原因与评审点 |
| --- | --- | --- |
| W01 | 新产品类型命名为“当前位置天气简报”，由 Agent 计划触发；原生时钟仍是单独委托 | 避免把普通计划通知冒称为已核验的 DeskClock 闹钟 |
| W02 | 动态模式 `CURRENT_AT_TRIGGER` 每次到期重新定位；另提供显式 `FIXED_CITY` | 车辆可能跨城；固定城市是用户选择的独立语义，不是动态定位失败后的隐形替代 |
| W03 | 位置在 Host 取得，Launcher 只发起权限/UI 请求；优先 Android 平台 `LocationManager`，OEM 定位适配器为可替换端口 | LineageOS 不应强依赖 Google Play services；不同 ROM 的后台行为需认证 |
| W04 | 位置坐标只在内存中用于城市解析；运行持久化归属城市 ID、名称、时区、位置时间和精度等级 | 恢复后重试天气查询仍能固定本次城市，不保留不必要的精确轨迹 |
| W05 | 天气能力使用受限 `WeatherProviderPort`；首个生产候选为和风天气，数据源最终由凭据、授权和目标 ROM 网络认证决定 | 不复用研究用 `web.search`，不允许模型给任意 URL |
| W06 | 查询“当天”以**发生时定位城市的时区与当地日期**为准；响应记录查询时间与预报有效时段，观测/发布时间仅在数据源实际提供时展示 | 防止 UTC 日界、跨时区移动、过期缓存造成错报，不伪造 v1 未给出的时间字段 |
| W07 | 到点先发可更新的提醒，再异步定位、查天气、更新同一通知；后续更新不重复响铃 | 把触发准点性与网络/定位耗时分开；最终天气失败仍有触发回执 |
| W08 | 天气简报默认确定性生成；模型润色仅是后续可选步骤，只能依据结构化天气事实 | 降低延迟、费用和编造风险 |
| W09 | 定位、天气查询均为只读步骤且可有界重试；通知/TTS 交付保持原有事务、渠道和勿扰策略 | 继续复用去重、预算、取消和分渠道回执 |
| W10 | 用户原话含“闹钟”且同时要求天气时，交互层说明会创建 Agent 天气提醒；若用户明确要求 DeskClock 响铃，须拆成两个独立操作并分别报告结果 | 标准闹钟委托与天气任务没有同一执行身份，不能假装组合已原子成功 |
| W11 | 动态模式每天 09:10 指**设备本地时间**，使用现有 `followDeviceZone` 对账；城市时区只决定天气的“当天” | 触发前尚不知道本次城市，不能假装已按未知城市的 09:10 排程；设备时区与城市时区不一致时显式提示 |
| W12 | 已启用计划后来失去定位/天气网络授权，仍保留到点触发并交付“内容不可用”；仅通知本身不可用才沿既有注册阻塞策略 | 天气是提醒内容，不应因内容授权撤销而悄悄取消用户的 09:10 提醒 |

## 3. 用户流程与授权

### 3.1 创建计划

对示例句，解析为：`DAILY 09:10`、`CURRENT_AT_TRIGGER`、`WEATHER_BRIEF`、通知交付。动态模式触发按设备本地时区，用户改变系统时区时沿既有时间变化对账；城市时区只用于选择当天的天气数据。预览明确展示下一次发生的日期、设备时区、“每次重新定位”、天气来源、联网需求及预计的权限。若设备时区与到期时解析出的城市时区不一致，运行详情说明 09:10 是按设备时区触发。固定城市模式则默认按该城市时区排程；两种模式不能自动互换。

“制定、设定、创建闹钟/提醒”必须在可信交互输入的写意图识别中覆盖；“告诉我”不能把同句中的创建动作降为只读。分类模型超时后也应得到安全且可解释的判定，不能放宽 `PolicyEngine` 的只读写入门禁。中文钟点解析覆盖“九点十分”“上午九点十分”“9:10”等，并对“九点左右”、多时刻及跨天含糊表达要求澄清。创建/预览均复用同一规范化时间与 `ExplicitScheduleIntent`，不得只给模型提示词补丁。

计划创建时要把**当前位置、联网获取天气、可选播报**作为三个可见的授权选择。请求天气并不等于已获位置权限或任意联网权限；权限页展示来源及可能传出的城市/粗位置。定位许可在 Launcher 的前台交互中请求，Host 在每次执行时复验；创建时权限未取得，动态位置计划保持草稿/阻塞状态，用户可改选固定城市。已启用计划后来失去定位或天气网络授权时，保留到点注册并交付“天气内容不可用”；将内容健康标为阻塞，不能复用现有“通知渠道不可用则撤除未来闹钟”的注册健康逻辑，也不得把旧城市天气冒充当前位置。

### 3.2 触发与展示

一次发生仍由 `ScheduleRun` 和固定 `occurrenceKey` 唯一标识。接收器只做受理、冻结本次模板/授权与“已到点，正在准备天气”的有界本地通知，然后交给既有执行图。它不等待 GPS、GeoAPI 或天气 HTTP。天气成功后以相同 `runId`/通知 ID 更新内容，显示城市、当前天气、当天最高/最低温、降水概率、数据时间与来源；内容更新不再次播放提醒声。若要求播报，按既有勿扰、通话、夜间、焦点和交付截止判断，播报未发生时记录部分交付，不把通知当成已听到。

“已到点”通知是时间触发的交付事实，“天气可用/过期/不可用”是内容步骤事实；运行页分别呈现 `scheduledAt → receivedAt → locatedAt → weatherRetrievedAt → deliveredAt`。先发通知不代表天气步骤成功，天气失败时最终状态为可解释的部分结果，而不是笼统 `SUCCEEDED`。

## 4. 定位域

### 4.1 接口与信任边界

引入 Host 内部 `LocationProviderPort`，返回一次有界的 `LocationFix`：坐标、水平精度、fix 时间、来源和取消句柄；再由 `CityResolverPort` 得到城市 ID、名称、行政区和时区。原始坐标不交给模型或 Launcher，不写通用日志；天气查询所需坐标仅在单次调用内使用。若使用城市 ID 查询天气，持久化本次城市解析结果便足以在进程恢复后继续天气只读步骤；不得为了方便重试而保存历史精确坐标序列。

平台实现优先 `LocationManager.getCurrentLocation()`，带取消与硬截止。它可能返回 `null`，后台获取失败概率也更高；`getLastKnownLocation()` 只能提供缓存结果，必须检验时间、精度和跨城风险，不能直接称为当前位置。[Android LocationManager](https://developer.android.com/reference/android/location/LocationManager)。OEM 若已有可信车辆位置接口，可以作为另一个 Provider，但其权限、更新频率和 user 0/Actor 边界仍需独立认证。

拟定首期阈值（需真机校准）：新定位最多等待 8 秒；候选缓存位置不超过 5 分钟、水平精度不差于 5 公里。城市边界附近或城市解析不唯一时，宁可提示位置不确定，不猜测城市。阈值是产品策略，不是 Android API 保证；长时停放、隧道、关闭系统定位、飞行模式和跨省移动都应实测。动态模式的定位失败，若用户显式设置了备用固定城市，可降级为“备用城市天气”，必须在通知显著标注；没有备用城市则报告天气无法确定，不能退回计划创建时城市。

### 4.2 权限与后台执行

首期粗定位 `ACCESS_COARSE_LOCATION` 足以服务城市级天气；细定位只有经评估证明必要时才申请。每天到点可能是冷启动、锁屏或后台执行；Android 10+ 后台位置访问涉及 `ACCESS_BACKGROUND_LOCATION`，Android 14+ 对后台启动使用 while-in-use 定位许可的前台服务还有额外限制。精确闹钟的后台启动例外**不自动授予后台位置读取权**；若采用 location 类型 FGS，须按其类型声明、权限与启动条件设计，不能把现有 specialUse 服务改个名称便视作通过。[后台位置权限](https://developer.android.com/develop/sensors-and-location/location/permissions/background)、[后台 FGS 限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)、[FGS location 类型](https://developer.android.com/develop/background-work/services/fgs/service-types)。

T00 必须先在目标 ROM 实测前台、锁屏、Host 冷进程、深度 Doze、定位关闭/撤权及不同精度授权。若后台定位无法稳定获得或无法向用户提供合理授权路径，则**不开放 `CURRENT_AT_TRIGGER` 定时模式**，仅开放 `FIXED_CITY`；不能以 system UID 的偶然可用性替代权限契约。定位只在用户授权的发生窗口请求一次，不持续采样。

## 5. 天气域

### 5.1 Provider 与数据契约

新增 `WeatherProviderPort.today(cityId, localDate, zone, deadline, cancellation)`，返回最小、可核验结构：`provider`、`cityId`、`cityName`、`localDate`、`conditionCode/text`、`temperatureNow?`、`min/max?`、`precipitationProbability?`、`observationTime?`、`forecastIssuedAt?`、`validFrom/Until?`、`retrievedAt`、`attribution`。缺字段就不生成对应断言；“实时观测”和“当天预报”分别标注，不把最高温误称当前温度。Tool `verified=true` 只表示响应结构/来源/有效期通过核验，不表示天气预报一定准确。

和风天气是首个生产候选：其[城市搜索](https://dev.qweather.com/docs/api/geoapi/city-lookup/)能解析城市及其时区；当前实现使用[实时天气 v1](https://dev.qweather.com/docs/api/weather/weather-current/)与[每日预报 v1](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)，避免采用官方已标记即将弃用的 v7 城市天气接口。v1 当前响应没有独立观测时刻，每日响应没有明确的预报发布时间；实现仅报告查询时间和预报有效时段，**不得将查询时间冒称发布时间或观测时间**。这些字段的完整性仍属于 WAC08 的待验缺口。当前 API 支持 JWT/API KEY 身份认证；凭据不得进入仓库、SDK、通知、模型提示或日志。[项目与凭据](https://dev.qweather.com/docs/configuration/project-and-key/)。API Host 固定、HTTPS、禁止跨域重定向、响应字节上限、取消与总 deadline 沿用现有 `PinnedWebSearchTransport` 思路；不能把 `web.search` 的百科/学术域名白名单扩成任意天气网页。

正式选型前核对目标部署许可、额度、网络可达性与[来源标注要求](https://dev.qweather.com/en/docs/terms/attribution/)。天气缓存仅按单个已授权城市及合理时效使用，不批量建立地理信息索引；官方对缓存时效和 GeoAPI 批量缓存另有[约束](https://dev.qweather.com/docs/best-practices/cache/)。Open-Meteo 可用于评估适配端口，但其[免费 API 只允许非商业用途](https://open-meteo.com/en/terms/)；车机产品不能把免费层当作默认商用后端。

### 5.2 授权与失败语义

注册新的只读 `weather.today` 能力，参数只允许已解析城市 ID/本地日期，不接收模型任意 URL。自动运行的 `ExecutionScope` 必须同时允许该能力与网络，Host 在调用前后检查 epoch、计划 revision、取消、user 0、凭据/网络策略；天气提供商响应是**外部数据**，不得进入指令通道。网络失败只对幂等读取做一次有界重试；`429`、凭据失效、响应格式错、数据超期与无网络分别记录，不凭模型生成“合理天气”。

若存在同一城市、同一当地日期且仍在明确时效内的已核验缓存，可用作带时间戳的降级内容；超期则不报天气。建议首期实况缓存最多 30 分钟，当日预报按提供商更新时间/有效时段判断，并参考提供商的实际更新策略调节。所有来源标注与时间戳跟随通知、运行详情及可选语音文案。

## 6. 工作流、持久化与预算

新增不可变模板 `daily_weather_current` v1；固定城市可复用同一模板加位置模式参数。推荐步骤：

| 顺序 | 步骤 | 失败处理 |
| --- | --- | --- |
| 1 | `resolve_city`：本次定位或读取用户固定城市，冻结本次城市 ID/时区/位置时间 | 动态模式无法确定城市时产生明确缺失状态；不冒充任务未触发 |
| 2 | `fetch_weather`：按本次城市与当地日期查询实况/当天预报 | 只读、有界重试；可使用合规且显式标记的短期缓存 |
| 3 | `compose`：确定性生成简报或失败文案 | 不调用模型生成天气事实；可处理前两步的缺失状态 |
| 4 | `deliver`：更新同一通知、按授权尝试播报 | 延续现有通知/TTS 分渠道回执；天气失败也交付解释 |

本模板仅有一个正式 `DELIVER` 步骤。§3.2 的到点占位通知属于 Schedule admission 的受限早期回执，不把它伪装成第二个工作流交付步骤。现有 `WorkflowStore` 对可选前置失败与必需步骤依赖的语义需评估：若其失败传播会阻断 `compose`，实施时应增加**显式的状态输入/降级路径**，不能把真正的定位/天气失败记为成功来绕过 DAG。占位与最终更新使用稳定 `runId` 派生的通知 ID，进程恢复或广播重投不能多响一次。

建议天气模板沿 `INTERACTIVE` profile 的现有 120 秒父活跃上限实施更窄的模板预算：定位 8 秒、天气总计 16 秒（含一次重试）、格式化 2 秒、交付 10 秒，父活跃墙钟上限 45 秒；并发重叠只计一次。最终数字须以目标 ROM 冷启动、网络超时与 UI 体验实测校准。受理、定位、查询、格式化和交付分别持久记录实际起止时间；离线或权限拒绝尽早结束，不耗满 45 秒。

计划冻结内容增加位置模式、备用城市、提供商策略版本、是否允许位置/网络/播报及模板版本；改变这些授权或位置字段增加计划 revision 和必要的 ruleGeneration/effectiveFrom，已领取运行使用冻结快照。运行只存最小城市级位置凭据与天气结果/失败码，遵守现有 SQLCipher、epoch、reset-pending、30 天/1000 条保留和数据清除语义。是否需要新表或只扩展有界模板参数/步骤输出，待 T02 比对现有 Room 20 schema 后决定；若调整 SDK DTO，按 ParcelSchema 追加字段并验证旧客户端读写边界。

## 7. 失败、撤权和交付矩阵

| 场景 | 本次结果与用户可见内容 |
| --- | --- |
| 定位许可创建时未取得，或已启用后被撤销 | 新动态计划留在草稿/阻塞；已启用计划仍到点提醒并将内容标为不可用，不执行当前位置查询，不借旧位置伪报 |
| 定位服务关闭、超时、精度不足或城市有歧义 | 有显式备用城市时标注备用；否则“已到点，无法确定当前位置，未查询天气”；记录位置失败码 |
| 天气服务超时、无网络、限流、凭据无效 | 到点提醒仍保留；短期有效缓存须标时间与非最新，否则更新为“天气暂不可用”；记录具体失败码 |
| 实况有而预报无，或反之 | 只报告已有字段，并标记部分天气内容，不推断缺失的温度/降水 |
| 通知渠道关闭或系统权限撤销 | 按现有通知阻塞/草稿与交付失败语义处理；不能把数据库运行成功当成用户已收到 |
| 勿扰、通话、无音频焦点 | 通知与播报分渠道记录；不越过系统静音，整体交付可为 PARTIAL |
| 进程死亡、重启、同一闹钟重投 | 按 `scheduleId + occurrenceKey` 去重，天气只读步骤可恢复；不重复创建计划或播放到点声 |
| 设备跨城、跨时区、时间手动变化 | 每次发生冻结当次城市/当地日期；仍沿单臂对账与原发生身份规则，不重新执行已消费时槽 |

通知先响而天气后到是本方案的预期行为。UI 应分别展示“提醒已送达”和“天气获取失败/成功”，不能用一个绿色勾代替两者。

### 12.1 当前设备 T00 结果与准入决定

设备序列号 `977d27c4`（Mi 9 SE、LineageOS、Android 15）已安装平台签名 debug Host/Launcher。设备的系统定位开启，Host 粗定位和后台定位权限均显示已授予；但 `dumpsys location` 没有 `network` Provider，`fused` 的本次请求实际转交 GPS。冷进程探针连续两次在约 8 秒返回 `LOCATION_UNAVAILABLE`，没有取得可核验城市；未记录或输出经纬度。因此**不能宣称该 ROM 的动态当前位置定时模式通过认证**。新建动态计划在缺少城市级后台定位源时保持草稿，并提示选择固定城市。即使未来 ROM 提供该 Provider，也仍需再做锁屏和 Doze 的实际到期测试。

同机的合成私钥探针确认短时 JWT 可以签发；设备系统 JCA 对 PKCS#8 Ed25519 私钥的原生导入失败后，实施改用版本固定的 Bouncy Castle 1.86。合成通知探针确认占位通知和静默天气更新均被 NotificationManager 接受，最终同一 `runId` 通知使用天气更新渠道；这只验证通知机制，**不是**真实 AlarmManager 到期或天气 API 成功。

### 12.2 原示例的模型失败复核与修复

2026-10-06 的真机重放显示：意图分类接口约 3 秒超时后安全回退；随后配置中的 `glm-5.3-flash` 走 Anthropic Messages 的结构化 JSON 兼容路径，在完整计划阶段返回 `finish=LENGTH`、工具调用数 0、可见正文长度 0。原代码将这个不完整响应归为通用 `MODEL_CALL_FAILED`，页面因此显示“模型调用失败”。新增类型化截断终态后，此类失败会显示“模型输出被截断”，不会采纳部分 JSON 或执行其工具建议。此诊断仅说明本次设备返回的结束原因，不推断服务端内部 token 分配。

对原话“那制定每天十点十分的闹钟，并告诉我当天的天气情况”，本地受限计划入口在真机经 `PolicyEngine → ToolExecutor → schedule.create` 创建草稿；2026-10-06 11:00 的一次复验耗时约 0.5 秒，终态 `LOCAL_PLAN_DONE / SUCCEEDED`，页面显示“已保存每天 10:10 的 Agent 天气提醒草稿，尚未启用”。随后在任务中心核对为草稿，并删除复验产生的重复草稿，只保留一项。它不能替代任意自然语言的模型规划，也不代表天气数据链路已通过实网验证。

### 12.3 当前明确缺口

1. 用户尚未配置和风天气 API Host 与 API Key/JWT，因此固定城市的真实查询、城市搜索、额度/许可和最终通知内容仍不可端到端验证；代码会保留草稿或给出 `WEATHER_NOT_CONFIGURED`，不生成伪天气。
2. v1 实况/预报不返回独立的观测时刻/预报发布时间。v0.2 已把 W06/WAC08 修订为只使用可核验的查询时间、有效时段，缺失字段不补造；若产品仍要求精确观测/发布时间，需另选提供该字段的非弃用数据源。
3. 没有持久或内存天气缓存；故网络失败时直接报告内容不可用。显式备用城市已实现，但仅在定位操作失败且定位授权未被撤销时使用，并在通知中标注。
4. 设备不能在当前环境给出冷启动定位结果；跨城、深度 Doze、真实 09:10 到期、提供商 429/撤权与 TTS 声音效果均不得标记为真机通过。
